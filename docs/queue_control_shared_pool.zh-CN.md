# QCTL 共享控制池与四条缓存

当前 main 已接入共享池，并适配 ICU JSON 参数化和定时 DMA 的 QCTL 提交/PRIME。以下隔离基点记录为历史证据；本次 main 集成验证见 SOFTWARE 的 `docs/queue_control_shared_pool_main.zh-CN.md`。

实现基点：SOFTWARE `6f3473e`、CModel `c0988ab`。本任务在两个工程的 `out/qctl-shared-pool` worktree、分支 `codex/qctl-shared-pool` 中实施，未覆盖 main 上同时进行的 ICU 参数化和 DMA 程序装载工作；未提交、未推送。

## 存储与控制

每任务每芯片使用一个 512 条共享控制池，按最终队列顺序紧凑装载，单队列仍最多 16 条。每队列保留 4 条缓存、独立的目录与取数/退休游标。Native 绑定只做源指令和释放计划校验，不进入控制池；其文件分区上限仍为 256 条。

共享池是一个真实单读端口模型：每物理拍最多发起一次读取，读延迟 2 拍，请求启动间隔 1 拍，响应流水最多容纳 2 项。请求获准时预留缓存位置，缓存占用加在途响应不得超过 4。轮转仲裁在全片每拍执行一次，队列等待事件时也继续读取和捕获响应。任务切换清除响应流水并更新控制池 generation，旧句柄明确拒绝。

共享模式的队列不保存完整控制分区副本。执行只读取缓存，不通过共享 RAM 的无延迟窥视判断控制边界。控制表退休仅推进本队列游标。`execute_synchronization()`、MEM transport executor、页面实际 SRAM 提交、原生释放相位保持原实现；已经发出的 FU 流水继续执行。

缓存不足时明确报错，不能等待取数后暗中增加计算拍。空分区保留 `end_cycle`，不消耗控制池记录。

## 预取和保守供给检查

PRIME 为各队列预装 `min(count,4)` 项，并行运行真实 Macro 解码前端。之后只要有剩余记录及缓存信用，就申请读取；不依赖低水位触发。

最终链接和最终镜像装载都检查共享池总容量、单队列容量及供给条件。令 D 为缓存深度，N 为可能需要运行期补充的队列数，I 为共享端口启动间隔，R 为读取延迟，采用保守补充界 `D*N*I + R + 1`。

对于初始缓存之外的第 j 条记录，从第 j-D 条控制退休到第 j-1 条控制退休，必须提供至少上述补充窗口。窗口下界来自两端的 Lq 差，以及中间真实 MEM 同步包至少 `count-1` 拍的执行长度。忽略事件等待、DDR 延迟和额外 reservation 时间，避免依赖慢速搬运才成立；也不把各队列事件同时早到的一次回放当成最坏情况。所有源位置、MEM 包序号和实际包解码校验继续执行。

这是充分条件，会保守拒绝部分实际可以供给的控制序列。控制边界未知时不得继续计算；首版没有新增边界旁路缓存。候选 QLNK 配方不直接执行，供给证明在最终链接后完成。重新分页或重定位后重新校验。

## 配置、格式和兼容

目标 JSON 的 `icu` 中新增：

```json
"queue_control_storage_version": 1,
"queue_control_pool_capacity": 512,
"queue_control_pool_read_ii": 1
```

同时设置 `queue_control_capacity=16`、`queue_control_cache_depth=4`、`queue_control_read_latency=2`、`queue_control_read_ports=1`。storage_version=1 时端口属于全片共享池；0 为原有每队列独立 RAM 模型，且 pool 字段必须为 0。参数参与目标能力和 ABI 校验；不支持的目标拒绝装载，没有隐式退回独立 RAM。

容器 writer 使用 v40，在原 v39 硬件字段后追加以上三个小端 u32。QCTL encoding=1、24 字节文件记录、BARR encoding=1 和 packed-v1 均不变；共享 RAM 中执行记录仅包含 cycle/opcode/operand。没有在文件中复制第二份控制表。

四条读取路径都识别新硬件字段。旧 v39 读取时填充 storage_version=0 和零 pool 字段，保留其 ABI 与执行语义；读取兼容不表示旧独立 RAM 目标的文件可直接装入共享 RAM 目标。要执行旧配置，使用匹配的旧目标；要使用共享模式，重新编译/最终链接。

当前隔离基点使用直接装载与有限 PRIME，未将主线程新增的定时 DMA 完整程序装载工作合入。集成时必须让共享池目录/数据提交、事件准备和 PRIME 遵守该装载协议，不能直接套用旧的逐队列 QCTL RAM 写入接口。

每次执行 7 个运行期 page use、8 次预取和 331,776 次 tile 提交。两个最终镜像都通过 Native 降低后的执行镜像等价性，以及独立加载检查；比对涵盖计算、搬运、操作数、relocation、事件和释放相位。CSV 只统一 Read/Read3D 等表示及前端诊断字段，不按队列平移或删除空拍。逐拍等价限定于 RUN 起点对齐后的主执行阶段。

与之前独立 RAM＋8条缓存的已验证结果相比，主执行周期不变。seq32 PRIME 从 80 增至 296（+216），seq128 从 92 增至 296（+204）。加上初始页面准备和后置搬运，当前共享池总计分别为 149,474、454,867 拍；没有将新增预热作为免费开销。全程最大仲裁等待为 97 拍，包含 98 个非空队列的 PRIME 竞争；RUN 的供给证明只计需要补充的 16 个队列。

两种程序都是350条伪控制、148条 Native 绑定，每队列伪控制峰值8条。seq32 最终文件485,270 B，计算 i-MEM 85,876 B、transport 2,496 B；seq128 最终文件1,852,437 B，计算 i-MEM 214,472 B、transport 2,496 B。QCTL 文件块均为13,868 B，QLNK分别为340,763 B与1,547,396 B。共享池减少物理预留容量，不删除文件里的校验/重新链接元数据；v40 额外增加12字节硬件字段。

小型日志、轨迹比较摘要、复现脚本及产物 SHA-256 见 [evidence/queue-control-shared-pool](evidence/queue-control-shared-pool/)。真实 CSV、最终文件及完整构建日志留在本 worktree 的 `out/validation` 和 `out`；构建使用 SOFTWARE 主入口下独立的 `out/qctl-pool-build`。
